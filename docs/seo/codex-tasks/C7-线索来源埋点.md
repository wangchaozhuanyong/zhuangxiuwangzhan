# Codex 任务 C7：落地页线索来源埋点

> 投放方式：整篇粘给 Codex。
> 前置：C1 / C2 页面已存在，且表单能正常提交。

---

## 1. 项目背景（自包含）

仓库 `flashcast-website`，三语站。

表单链路是固定的，`AGENTS.md` 明确规定不许改：

- 表单提交固定走 Supabase Edge Function **`submit-lead`**（`supabase/functions/submit-lead/`）
- 通知固定走 `notify-lead`、`notification-settings`、`maintenance-reminder`
- 现有返回格式先保持不动：`{ ok, id }` / `{ error }`
- 相关表：`leads`、`form_attempts`（防刷），迁移在 `supabase/migrations/`
- 前端提交逻辑在 `src/lib/`（搜索 `submit-lead` 的调用点）

**问题**：新增 5 个交叉页 + 7 个业务线页后，所有线索都长得一样，三个月后无法判断哪一页真的带来客户。

## 2. 本次目标

让每条线索都带上「来自哪一页」的信息，且能在后台线索列表看到。

具体：
- 表单提交时附带 `source_page`（落地页 slug）与 `service_slug`（如果可推导）
- 数据落到 `leads` 表（现有列或新增列）
- 后台 `/admin/leads` 列表能看到来源
- `submit-lead` 的请求/响应契约**保持向后兼容**

**既定答案**：属 `leads` 模块。前端表单在展示层，业务规则在 Edge Function 一侧，数据列变更走迁移。**不要新建第二个 Edge Function。**

## 4. 允许修改 / 禁止修改

**允许**：
- `supabase/functions/submit-lead/`（新增可选字段的接收与存储）
- `supabase/migrations/`（新增列，增量迁移）
- 前端表单提交处（`src/lib/` 下相关文件、表单组件）
- 后台线索列表展示（`src/pages/admin/` 下线索相关页面、`src/i18n/` 里的 admin 文案）

**禁止**：
- 不要改 `submit-lead` 现有的返回格式（`{ ok, id }` / `{ error }`）
- 不要新建独立 API 或第二个 Edge Function
- 不要用脚本直接写 `leads` 表
- 不要在前端做「来源校验后拒绝提交」——旧客户端/旧页面不能因此失败
- 不要在日志里输出客户隐私字段（`AGENTS.md` 日志隐私规则）

## 5. 硬性要求

1. **字段命名统一**：
```
source_page: string     // 例 "locations/kuala-lumpur/kitchen-renovation"（不带语言前缀）
source_lang: string     // "en" | "zh" | "ms"
service_slug?: string   // 例 "kitchen-renovation"
area_slug?: string      // 例 "kuala-lumpur"
```

来源应从 **路由参数** 推导（`/:lang/locations/:area/:service`），不要从 `document.referrer` 猜。

2. **语言前缀必须剥离**。存 `locations/kuala-lumpur/kitchen-renovation`，不要存 `en/locations/...`，否则同一页会被算成三条不同来源。

3. **向后兼容**：所有新字段都是**可选**。旧值缺失时存 `null`，不报错。`submit-lead` 收到缺字段的请求必须照常成功。

4. **数据库变更走增量迁移**：
   - 新建 `supabase/migrations/{timestamp}_add_lead_source_columns.sql`
   - 用 `ADD COLUMN IF NOT EXISTS`，不要改既有列
   - 需要索引时，只对实际会筛的列建（如 `source_page`）

5. **后台可见**：
   - `/admin/leads` 列表增加「来源」列
   - 来源显示为**人能看懂的文字**，不要直出 `locations/kuala-lumpur/kitchen-renovation` 这种技术串（`AGENTS.md` 的「用户界面禁止直出技术字段」规则）
   - 三语文案齐全（`src/i18n/admin*Text.ts`）

6. **筛选**：列表支持按来源筛选（可选，但如果有筛选功能，必须能选到新来源）。

7. **防刷不变**：`form-attempts` 逻辑不受影响，新增字段不参与防刷判定。

## 6. 验收标准

- [ ] 从 `/en/locations/kuala-lumpur/kitchen-renovation` 提交一条测试线索，`leads` 表里 `source_page = "locations/kuala-lumpur/kitchen-renovation"`、`source_lang = "en"`
- [ ] 从 `/zh/locations/kuala-lumpur/kitchen-renovation` 提交，`source_lang = "zh"`，`source_page` 相同（不带 `zh/`）
- [ ] 从 `/en/contact` 提交（旧路径），新字段为 `null`，提交依然成功
- [ ] 后台 `/admin/leads` 能看到来源，且显示为可读文字
- [ ] `submit-lead` 返回格式与改动前完全一致
- [ ] 迁移可重复执行（`IF NOT EXISTS`）

## 9. 边界处理

| 情况 | 处理 |
|---|---|
| 需要给 `leads` 加 4 个列，但 `leads` 表已有类似字段 | 先核对现有列，能复用就复用，报告列名映射 |
| 后台线索列表改动影响导出/报表 | 说明影响范围，导出功能同步加字段或说明不加的理由 |
| 无法本地起 Supabase | 迁移只做 SQL 层核对，并在报告里标「未实测」，不要声称已验证 |
