# Codex 任务 C2：新增 7 个业务线服务页

> 投放方式：把本文件整篇粘给 Codex。
> 前置：无。可与 C1 并行。

---

## 1. 项目背景（自包含）

仓库 `flashcast-website`，Vite + React，三语（`en` / `zh` / `ms`），路由带 `/:lang/` 前缀。

服务数据两处来源，**优先级是 CMS 高、静态低**：

- 静态 fallback：`src/data/services.ts`（`ServiceItem[]`，11 条），类型定义在 `src/data/types.ts`
- CMS 数据：Supabase `services` 表，通过 `usePublishedServices` / `usePublishedServiceBySlug`（`src/hooks/usePublishedContent.ts`）读取

`src/pages/ServiceDetail.tsx` 里的实际逻辑是：

```ts
const services = cmsServices?.length ? cmsServices : fallbackServices;
```

**这意味着：只改 `services.ts` 不会改变线上表现**，因为 CMS 有数据时静态数据被忽略。这一点本任务必须处理，见第 5 节第 8 条。

## 2. 本次目标

新增 7 个服务，走现有路由 `/:lang/services/:slug`，**不新增路由**：

| slug | 业务 | 特殊性 |
|---|---|---|
| `digital-lock` | 电子锁 / 智能门锁 | 产品型：型号、门厚兼容、安装费、保修 |
| `painting` | 刷漆 / 油漆工程 | 按 sqft 计价、色卡、旧墙处理 |
| `tiling` | 地砖 / 瓷砖铺贴 | 按材料分类（homogeneous / porcelain / mosaic） |
| `ceiling` | 天花板 / 吊顶 | 石膏板、集成吊顶、灯槽 |
| `partition` | 隔墙 | 石膏板、玻璃、铝合金 |
| `electrical-plumbing` | 水电 | 按点位计价，最高频询价项 |
| `factory-renovation` | 工厂装修 | B2B：承载、消防、通风、停业成本 |

**既定答案**：

- 7 个都属于 `services` 模块，不新建模块；
- 只改 `src/data/services.ts` 追加条目，不动既有 11 条；
- **优先用现有 `ServiceItem` 字段承载**，不要为这 7 个服务扩类型。映射方式：
  - 「型号 / 门厚 / 安装费 / 保修」→ 放进 `items`（字符串清单）和 `faqs`
  - 「按 sqft 计价 / 按点位计价」→ 放进 `description` 和 `faqs`
  - 「消防 / 通风 / 承载」→ 放进 `items`
- 只有当三个以上服务都需要同一个新结构化字段时，才考虑改 `src/data/types.ts`，并且必须单独说明理由。

## 4. 允许修改 / 禁止修改

**允许**：
- `src/data/services.ts`（追加 7 条）
- `src/data/types.ts`（仅在上面第 3 节的条件下，且需说明）
- 如需专用展示组件：`src/components/services/` 下新建

**禁止**：
- 不要改既有 11 条服务的任何字段
- 不要新增一级模块
- 不要把 7 个服务合并进 `renovation` 一个页面
- 不要新增路由

## 5. 硬性实现要求

1. **每个服务必须有的字段**（缺一不可）：
   `id`、`title`、`titleZh`、`slug`、`seoTitle`、`seoTitleZh`、`seoDescription`、`seoDescriptionZh`、`summary`、`summaryZh`、`description`、`descriptionZh`、`suitableFor`、`suitableForZh`、`commonProjects`、`commonProjectsZh`、`processSteps`、`processStepsZh`、`items`、`itemsZh`、`faqs`、`faqsZh`、`image`。

2. **三语齐全**：`ms`（马来语）不要求写在静态文件里（现有 11 条也没有），但**必须不能让 ms 页面显示英文或空**——沿用现有 fallback 机制，并在交付报告里说明 ms 当前的实际表现。

3. **title 长度**：英文 `seoTitle` ≤ 60 字符，中文 `seoTitleZh` ≤ 30 字，且必须包含「服务词 + 区域词」（例：`Digital Lock Installation KL | Supply & Install | FLASH CAST`）。

4. **禁止编造**：
   - 不要写真��价格（`RM 800` 这种）——用「由现场测量与型号决定」这类表述
   - 不要编造保修年限（写「以报价单条款为准」）
   - 不要编造品牌独占代理关系
   理由：这些数字必须由业主提供，AI 编造的报价会直接损害转化和法律责任。

5. **`digital-lock` 单独处理**：它是产品型服务，页面需要能列型号表。用 `items` 承载型号与兼容门型，`faqs` 承载安装与保修问题。不要在 `ServiceItem` 上硬加 `products` 字段。

6. **`factory-renovation` 单独处理**：B2B 语气，重点写工期与停业成本、消防合规、地面承载、通风。不要用住宅装修的「温馨」「设计感」措辞。

7. **图片**：`image` 字段必须指向真实存在或明确标记为概念图的资源。现有模式是 `/images/services/ai-concepts/xxx.webp` 用于概念图。**新服务的图如果不存在，先复用同类图并在报告里列出缺图清单**，不要引用不存在的路径（会导致 404 和 CWV 掉分）。

8. **必须处理 CMS 与静态的落差**（最重要的一条）：
   - 交付时要明确说明：新增的 7 条只存在于静态 fallback
   - 线上如果 `services` 表已有数据，这 7 个页面可能读不到新内容
   - 给出一份「后台录入清单」：哪 7 条需要在 `/admin` 的服务管理里创建，字段对应关系是什么
   - **禁止**写脚本直接 insert 到 `services` 表。`AGENTS.md` 明确禁止绕过后台发布链路。

## 9. 边界处理

| 情况 | 处理 |
|---|---|
| `ServiceDetail.tsx` 有硬编码的 slug 分支（如 `slug === "design"`、`"surface-repair"`） | 检查是否需要为新 slug 加分支；若不需要，明确说明为什么 |
| 某个服务需要独立版式（如 digital-lock 的型号表） | 优先用现有渲染；确需独立版式再建子组件，并说明为何现有结构承载不了 |
| 发现 `services` 表缺少某字段 | 输出字段缺口清单，交回业主决定是否加迁移，不要自行加迁移 |
