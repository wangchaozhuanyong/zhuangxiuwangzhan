# Codex 任务 C1（v2 修订版）：新增「服务 × 区域」交叉页路由

> 投放方式：整篇粘给 Codex。
> **v2 修订原因**：Codex 的只读核对指出「200/404 由 React 渲染 + 中间件 manifest 两层共同决定」，经复核**成立**，且比它描述的更严格——见第 2 节。原 v1 的允许修改清单没有覆盖 manifest 生成链路，会导致新路由全部 404。本版已修正。
> **必须配套投放**：[C1-manifest-meta-values.md](C1-manifest-meta-values.md) —— 内含 15 条可直接粘贴的三语 manifest 定义。没有这个文件，Codex 只能停留在骨架阶段，无法通过 HTTP 200 验收。

## 1. 项目背景（自包含）

仓库 `flashcast-website`，Vite + React 单页应用，三语（`en` / `zh` / `ms`），所有公开路由带语言前缀 `/:lang/`。

现有两层公开页面：

| 层 | 路由 | 文件 | 数量 |
|---|---|---|---|
| 服务总页 | `/:lang/services/:slug` | `src/pages/ServiceDetail.tsx` | 11 个 |
| 区域总页 | `/:lang/locations/:slug` | `src/pages/LocationPage.tsx` | CMS 侧 30 个区域（manifest 有 60 条 en+zh），静态 `src/data/locations.ts` 8 个 + 15 个案例型 |

**缺口**：没有「某个区域的某项服务」这一层。

## 2. 关键事实：200/404 由两层共同决定（已复核，比预想更严格）

这是本任务最大的坑，动手前必须理解。

`functions/_middleware.ts` 第 26 行：

```ts
import manifest from "./seo-manifest.json";
```

第 2526 行（`generatePublicHtml` 的返回处）：

```ts
const generatedResponse = new Response(transformed, {
  status: meta ? response.status : 404,
  headers,
});
```

第 2592 行（异常兜底路径）：

```ts
const fallbackResponse = new Response(transformed, {
  status: fallbackMeta ? 200 : 404,
  headers,
});
```

`meta` 的来源见第 2234 行附近：

```ts
const englishMeta = key.startsWith("/ms") ? manifest[key.replace(/^\/ms(?=\/|$)/, "/en")] : undefined;
const staticMeta = manifest[key] || (englishMeta ? { ...localizeMalayMaterialFallback(englishMeta, key), lang: "ms", canonical: ..., noIndex: true } : undefined);
```

### 由此推出三条硬结论

1. **React 能渲染 ≠ 用户能看到。** 路由注册了、组件写对了，只要 `functions/seo-manifest.json` 里没有该路径，中间件直接返回 HTTP 404。
2. **ms 不会自动继承。** ms 路径如果 manifest 里没有独立条目，会走 `englishMeta` + `localizeMalayMaterialFallback`，并且带 `noIndex: true`。这意味着 ms 交叉页即使能返回 200，也是 noindex 状态，收录价值为零。
3. **manifest 与 sitemap 是绑定的。** `scripts/generate-seo-manifest.mjs` 生成的 manifest 同时供中间件判定与 sitemap 生成使用；`buildQualifiedSitemap` 还有一条全局硬校验：任何一条 `source_complete === false` 或 `qualification !== "eligible"` 都会让**整个 sitemap 生成抛错** `seo_manifest_unqualified`。所以**不能**用「给交叉页标不合格」的方式来让它 200 但不进 sitemap——那会直接炸掉全站 sitemap。

## 3. 本次目标

新增第三层路由，**仅开放 5 个组合**：

```
/:lang/locations/:area/:service
```

| area | service | 三语 URL 总数 |
|---|---|---|
| `kuala-lumpur` | `kitchen-renovation` | 3 |
| `kuala-lumpur` | `office-renovation` | 3 |
| `kuala-lumpur` | `bathroom-renovation` | 3 |
| `petaling-jaya` | `condo-renovation` | 3 |
| `selangor` | `landed-house-renovation` | 3 |

合计 15 个合法 URL。**其余任何 area × service 组合必须是真 404，不允许 fallback。**

## 4. 动手前必须先做的核对（产出结论后才能写代码）

按顺序做，每项给出证据：

### 4.1 manifest 接入点核对

已知事实（已复核，可直接采信）：

- manifest 初始条目来自 `scripts/seo-static-pages.mjs` 的 `buildStaticManifest()`（`generate-seo-manifest.mjs:6` import，`:18` 调用）
- 该函数遍历 `staticDefs` 数组生成条目，def 结构为 `{ lang, path, title, description, keywords, ogImage, faqs, schemaType, entityName }`
- `generate-seo-manifest.mjs:194` 会给所有初始条目补 `snapshotProvenance(snapshot,"static_page",route,meta.lang,true)`
- `generate-seo-manifest.mjs:390-394` 在末尾**重算**所有条目的 `available_locales` 与 `hreflang`，依据是 manifest 里实际存在哪些语言的同级路径

**你要核对的是**：在 `staticDefs` 里追加 15 条（5 组合 × 3 语言）后，是否会出现：
- [ ] `available_locales` 是否被正确重算为 `["en","zh","ms"]`（而不是停在 `["en","zh"]`）
- [ ] `hreflang` 是否三语互通
- [ ] `source_complete` 是否为 `true`、`qualification` 是否为 `"eligible"`（否则 sitemap 会抛错）
- [ ] `owned_static` 是否为 `true`，以及这对 sitemap 边缘过滤（`_middleware.ts:2008`）有什么影响

### 4.2 内容记录入口核对

核对现有 `service_areas` 表与 `services` 表的记录能否直接支撑 `/locations/{area}/{service}` 的页面数据，还是需要页面自己组合两份数据。给出结论：
- 交叉页的 H1 / 面包屑 / 正文头部数据从哪个 hook 取（`usePublishedServiceBySlug` + `usePublishedServiceAreaBySlug`？）
- ms 内容若缺失，页面表现是什么（英文回退 / 空 / noindex）

### 4.3 部署与预览核对

确认 Cloudflare Pages 预览环境的变量配置是否足以让中间件正常读 Supabase；若预览环境无 Supabase 凭证，明确说明「预览站会是 200 但内容为空」，并给出验收时如何区分「200 + 有 SEO meta」与「200 + 空内容」。

## 5. 方案选择：manifest 怎么接（三选一，推荐 A）

### 方案 A（**推荐，本任务采用**）：在 `staticDefs` 追加 15 条静态定义

- 改动文件：`scripts/seo-static-pages.mjs`
- 优点：最小改动、不碰数据库、不碰中间件、可版本控制、评审容易
- 缺点：新增页面要改代码（首发只有 5 个组合，可接受）
- 数据形态：每个组合 × 每语言一条 def，`path` 为 `/locations/{area}/{service}`，`title`/`description` 用完整三语真实文案

### 方案 B（**本任务不做**，扩到 12–15 页时再评估）：由 CMS 派生

- 让 `service_areas` 表带 `service_slugs` 字段，manifest 从 CMS row 派生
- 需要迁移 + 后台 UI + `qualifiesLocale` 适配
- 本任务只输出可行性说明，**不实现**

### 方案 C（**禁止**）：在 `_middleware.ts` 里对交叉页路径特判

- 例如「`/locations/*/*` 两条路径段时跳过 manifest 检查直接 200」
- **禁止理由**：这会绕过 manifest 机制，导致 sitemap、hreflang、canonical 全部失去一致性来源，且 `noIndex`/`qualification` 判定失效。后续 C3 的收录校验会无从下手。

> 如果 Codex 认为方案 A 不可行（比如实测发现 `staticDefs` 的 schema 承载不了），必须**停止并输出原因 + 替代方案对比**，等确认后再动手。

## 8. 硬性实现要求

1. **不要用扁平 slug**。不实现 `/kitchen-renovation-kuala-lumpur`，只做 `/:lang/locations/:area/:service`。

2. **路由顺序**：`publicRoutes.tsx` 已有 `/:lang/locations/:slug`（第 81 行）和 `/:lang/locations`（第 80 行）。新路由必须能在两者之间被正确匹配，**改完必须实测 `/en/locations/kuala-lumpur` 仍然渲染区域页**，不能被交叉页吃掉。

3. **未知组合必须真 404**。两道防线都要有：
   - React 层：不在白名单 → 渲染 `<NotFound />`
   - 中间件层：因为不在 manifest，天然返回 404
   - 验收时必须用 HTTP 状态码证明，不能用「页面显示 404 文案」代替

4. **元数据入口用 `staticDefs`**，`title`/`description` 三语齐全（由内容侧提供，见第 12 节）。**不要**用占位符 `TODO` 或 `lorem`，因为一旦 PR 合并这些值就会进 manifest 与 sitemap。

5. **Schema 复用现成组件**（`src/components/JsonLd.tsx`）：
   - `JsonLdService`、`JsonLdFAQ`、`JsonLdBreadcrumb`
   - `JsonLdLocalBusiness` 的 `areaServed` 必须写具体区域名，不写 `Malaysia`

6. **`PageMeta`** 传 `canonicalPath`，三语 canonical 与 hreflang 互通。

7. **图片用 `SmartImage` / `DeferredSmartImage`**，禁止裸 `<img>`。

8. **页面内容只做骨架**：H1、区块容器、Schema、CTA 位、面包屑、区域/服务互链。**不要编造报价数字、客户案例、项目名**。

9. **登记交互合规**：`docs/interaction-route-compliance.json` 追加条目，字段对齐现有结构（`path`/`surface`/`source`/`loading`/`refresh`/`navigation`/`editing`/`acceptance`/`samplePath`/`component`），`acceptance` 必须是真实验收状态。

10. **`acceptance` 不许造假**。只有 dev 环境看过就写 `PASS_LOCAL_SIMULATED`，不要写笼统的 `PASS`。

## 12. 合并策略（**重要，必须遵守**）

因为 manifest 与 sitemap 绑定，C1 一旦合并，5 个交叉页就会进入生产 sitemap 并被抓取。而 C1 阶段页面正文还是骨架。

所以采用这个节奏：

```
1. C1 在 PR 分支完成，manifest 含 15 条三语真实 title/description
2. 在 Cloudflare Pages 预览站完成全部 HTTP 验收（第 9 节）
3. PR 先不合并
4. 内容侧补齐 5 页三语正文（L1）
5. 正文并入同一 PR，再合并上线
```

**Codex 本任务的终点是「PR 就绪 + 预览验收通过」，不是「已上线」。** 不要自己合并，也不要在报告里声称已上线。

如果业主明确要求 C1 单独上线（接受薄页面先被收录），那需要先确认这个取舍，不要自行决定。

## 13. 边界处理

| 情况 | 处理 |
|---|---|
| `staticDefs` 实测无法承载交叉页（如缺 `noIndex` 字段） | 停止，输出「缺什么字段 + 加字段的影响面」，等确认 |
| ms 条目实测仍带 `noIndex: true` | 输出 `englishMeta` 回退路径的触发条件，说明要满足什么才算独立 ms 条目 |
| 中间件把 `/locations/kuala-lumpur/kitchen-renovation` 当成 `/:lang/locations/:slug` 处理 | 输出中间件的路径解析逻辑（`dynamicRouteState` 相关），提出最小改动方案，**不要先把代码改了再解释** |
| 需要给交叉页加 `noIndex` 但 manifest 不支持 | 不要靠 `qualification: "ineligible"`（会炸 sitemap），输出替代方案 |
| 发现 `service_areas` 表已有 30 个区域而静态只有 8 个 | 记录这个差异，本任务只用 5 个白名单组合，不要顺手扩到 30 |
